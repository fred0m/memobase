## 1. 核心发现：temporal 0.667 → 0.194 是四个不同的问题被归因成了一个

「概要层时间词直通对 temporal 是负贡献」这个诊断，**只对 2/6 条查询（#19、#20）成立**。逐条分解：

| 查询 | T-D MRR | 真实根因 | 修复层 |
|---|---|---|---|
| #17 最近搞什么新系统 | 0.333 | **评测 harness bug**：直通日期升序取窗口内最旧 2 天（8/24-25）；插件生产代码降序取最新 2 天（8/29-30 = gold 所在日）。生产链路大概率命中 | 修评测排序 |
| #18 昨天配 search-combo | 0.333 | gold 全在 8/30（=今天）：flush 滞后 ±1 天日期漂移；rec=1.0，伤害轻微 | 单日窗 ±1 天 padding |
| #19 上周修了哪些东西 | 0.25 | **标注锚点错位**：「上周」gold=8/24-29 是周一 8/31 视角口径；EVAL_NOW 冻在周日，解析窗 8/17-23，差一周 | 修标注锚 |
| #20 上周点的瑞幸 | 0.25 | 同 #19：gold 8/24 出窗一天；直通拉 8/19-21 概要霸占注入头部，gold 被压到 rank 4+ | 修标注锚 |

| #22 最近一周新设备 | 0.0 | 同 #17：gold 全在 8/29，评测取 8/24-25；生产取最新 2 天（8/29+8/30）应直接命中 | 修评测排序 |

### 1.1 评测 harness 与生产行为的三处不一致

1. **直通日期排序方向**（最关键）
   - 评测 `eval_td_regression.py` L198：`ordered = sorted(docs.values(), key=lambda s: (s["summary_date"] not in direct_days, s["summary_date"]))` → 直通日期**升序**，取最旧 2 天。
   - 插件 `__init__.py`：`direct_summaries = sorted(s_list, ..., reverse=True)` → **降序**取最新 2 天。
   - 多天窗（「最近」0-6 天）场景下，两者取的日期完全不同；gold 集中在最近两天时，评测系统性低估生产质量。
   - **推论：不修这个 bug，方案 A 也过不了闸门**——「最近」类 ≤6 天直通仍开，评测仍取错日期，#17/#22 继续挂 0 分。
2. **语义路渲染**：插件渲染语义路命中文档（merged 后 top-2），评测只渲染直通日期文档（L254 `if d not in direct_days: continue`），语义路文档只占位不出行。
3. **header 计费**：插件把「【M/D 概要】…钻取提示」算进 350 预算（每文档约 40 字符），评测不计——评测的概要段有效预算反而更大，同样是偏差。

### 1.2 对照基线自身的混淆变量

- v3 基线事件段预算 **900**（`eval_memobase_vs_memu.py` L204 `budget=900`），T-D 事件段预算 **850**——对照实验同时改了两个变量。对照跑出 0.742 < 0.769 也说明 harness 与 v3 评测不等价。
- T-D 的 vector 腿 query 做了 `json.dumps` + `quote` 双重编码（L91），插件是原样传参（L603-610）——语义腿可能拿的是带引号花括号的「query」，相似度失真。需查证服务端如何解参。
- rerank 4 秒超时静默 fail-open（eval L166-167 `except Exception: pass`）→ 部分轮次 rerank 生效、部分轮次跳过，直接解释 0.618-0.714 的运行间波动。波动不是玄学，是可观测变量。

### 1.3 MRR@10 度量本身的系统性偏差

评测把注入序列当排名（`mixed = summary_events + event_events`），概要段事件前置被算成「霸占头部排名」。但生产中 LLM 读的是全文上下文——rank 12 的行仍在上下文里。MRR@10/Recall@10 对「开概要段」的配置系统性低估（尤其 SC-002 已知 12 条增益查询的收益被同一把尺子压扁）。建议双指标：**Recall@全注入集**（问「信息到没到上下文」）+ MRR@10（问「事件腿内部排序质量」）。

## 2. 四个决策问题的回答

### 2.1 方案选择：A、B、C 都不选，走 D（先修度量，再定点修）

**对 A（直通只对 ≤6 天窗生效）的评价**
- 方向感对（「概要层救聚合、事件层保精确」的分工），但工具太钝。
- 后果：>6 天窗全关直通 = 概要层**永远**帮不上「上周/上个月/今年」类查询——而稀疏老数据区间恰恰是事件腿最弱、文档形态最强（R2: 0.894 vs 0.110）的地方。用标注 bug 反向定义产品语义，本末倒置。
- 且如 §1.1 所述，A 修不好 #17/#22/#21，带着当前 harness 跑 A 大概率还是不过闸门。

**对 B（接受口径漂移，放宽判定）的评价**
- 内核对：闸门应区分「解析器错」vs「标注不一致」两类失败。
- 做法危险：现在的「漂移」一半是标注锚点错误（§1 根因表），放宽标准等于把标注错误烧进验收基线。
- 正确姿势是修锚后保持闸门严格，而不是降闸门迁就坏标签。

**对 C（不开 flag，等 60+ 查询）的评价**
- 被动。36 条已经足够诊断出 harness bug、截断问题、标注锚错位三个具体可修的问题，修它们比再标 24 条查询便宜得多。
- 60+ 扩充该做（见 §2.4 统计脆弱性），但它是方差问题，不是这三个根因的信息增量来源。

**方案 D（推荐）：三步走**

| 步骤 | 内容 | 工作量 |
|---|---|---|
| D1 修度量 | harness 直通排序对齐插件（降序取最新）；语义路渲染对齐；header 计费对齐；事件段预算回 900；查证 vector 腿双重编码；rerank 触发/跳过逐条落日志（或评测时 mock） | 半天内 |
| D2 修标注锚 | temporal 六条的 deixis 重锚：「上周」gold 重锚到周日语义（gold 改为 8/17-23 的事件），或查询改写为「这周/最近几天」匹配 gold 意图；「昨天」(#18) 二选一同理 | 1 小时 |
| D3 重跑 T-D | 修完 D1+D2 重跑，预期 temporal 回到 0.6+；届时再判断 #19/#20 是否还需要产品改动 | 一轮评测 |

**如果 D3 之后「上周」类仍失败**，产品侧用**直通降级软信号**替代 A 的硬 cutoff：

> 直通文档的 event_ids 与事件腿 fused top-k 无交集时（k≥5 且 overlap=0），概要段降级为后置注入（事件段在前）或只保留 header + 钻取提示。

- 原理：口径漂移的运行时特征恰好是「直通拉的日期」与「语义/关键词腿指向的日期」不一致。这个信号免费（event ids 双方都有）、自适应（未来的任何口径漂移都能接住）、可解释（日志可记 demote 原因）。
- 对照检验：#21「今天」类，事件腿 top 事件本来就是今天的（temporal boost 1.6× 加持），overlap 高 → 不降级 ✓；#19 型错窗，两腿指向完全分叉 → 降级，事件腿 gold 回前排 ✓；真日历「上周」查询，内容匹配与 boost 双双指向窗内 → overlap 高，不降级 ✓。
- 实现约 10 行，比 A 的 5 行多一点，但保留了概要层全部潜力。

### 2.2 时间窗设计：直通窗的更优解

**「上周」到底该怎么解析——三层修正：**

1. **日历周锚定替代固定偏移**
   - 现状：`_STATIC_TEMPORAL_PATTERNS` 里「上周」→ (7,13)。这是**周日极端值**：周日的「上周」确实是 7-13 天前，但周一的「上周」应是 1-7 天前，周四的「上周」是 4-10 天前。
   - 修正：按 ISO 周（周一始）解析——算出今天的 weekday，推 [上周一, 上周日]。CJK 上下文里用户心智模型基本是周一始周。
   - 注意：日历周解析**不能**修 #19/#20（周日跑评测，日历上周同样是 8/17-23）——那两条的病根在标注锚（D2）。但日历解析让其他六天的「上周」语义正确，独立于本轮回归。
2. **直通拉取窗 padding**
   - 解析窗 ±2 天 padding（仅用于直通拉概要，boost 窗可只 pad 1 或不 pad）：吸收口语「上周」的边缘模糊。
   - 单日窗（今天/昨天/前天/N 天前）**±1 天 padding**：吸收 flush 滞后 / 时区造成的 ±1 天漂移（#18 实测咬人，spec Edge Case 里也记录在案）。顺带把 #18 的根因修掉。
3. **中期正解：kind=weekly**
   - schema 的 kind 字段已经预留 weekly/monthly。「上周」直通变成拉 [上周, 本周] 两个周概要，topk=2 **天然覆盖两种口径**（周一视角和周日视角都在这两周内），日粒度洪泛（错误一天拉出 4-5 个非 gold 事件霸占头部）问题同时消失。
   - 周概要与「周」级查询的粒度对齐，是概要层分层设计的自然延伸；建议进 ROADMAP 而不是本期。

**不建议**：query-time LLM 时间词归一化。正则可解的问题不值得引入一次 LLM 调用的延迟与不稳定性。

**标注侧配套**：加一个 **deixis linter**——标注工具在标注时自动跑 `parse_time_window(query) @ EVAL_NOW`，校验 gold 日期 ⊆ 解析窗，不一致即报警。这次的锚点错位本该在标注阶段就被拦住；以后扩到 60+ 条查询时这条纪律必须有。

### 2.3 分段注入（350/850）的改进空间

按优先级：

1. **行内排序（#21 的正解）**
   - 现状：直通文档行按时间正序渲染，350 预算截断尾部。
   - 改法 A（推荐）：直通文档的行用**本地 BM25 按 query 打分行级分数**再截断——`hybrid_retriever.py` 里 BM25Index 现成、零依赖、零 API 成本。「上周我们修了哪些东西」的「修」、「今天聊了些什么」后的 gold 行内容词会被排到前面。
   - 改法 B（更简单）：直通文档行倒序（最新先行）。「今天聊了些什么」类查询晚间问，最新事件往往最相关。
   - 语义路文档保持原序（它的相关性已经由向量分保证）。
2. **单日窗自适应预算**
   - 直通只命中 1 天时，350 明显不够（30 事件 ≈ 1500+ 字符，覆盖率 ~20%）。建议 `summary_budget = min(700, 200 + 150 × 直通文档数)` 一类，或简单规则：窗宽 ≤1 天 → 700，多天窗 → 350。
3. **header 与钻取提示不计入内容预算**
   - 两个 header（~80 字符）+ 钻取提示是 affordance 不是内容，当前占了 23% 概要预算。评测不计、插件计，顺手对齐。
4. **对照公平性**
   - T-D 事件段预算改回 900，与 v3 基线对齐，消除 850 vs 900 混淆（~1-2 行的注入差异，恰好压在 gold 常在的尾部）。
5. **度量升级**（§1.3）：Recall@全注入集 + MRR@10 双指标。

### 2.4 没想到的坑与好点子

**坑：**

1. **语料密度伪影**：84% 事件在最近 4 天，8/14-8/18 空洞。R2 doc 形态 0.894 的优势部分来自密度——稀疏区「命中正确日期」≈「命中 gold」。随历史拉长，「最近」窗 7 天的 topk=2 文档只覆盖 2/7 天，覆盖率单调衰减。这是 weekly 概要与「topk 随窗宽缩放」的共同论据。
2. **闸门统计脆弱**：每场景 6-8 条，单条 ±0.5 MRR 振荡（R1 #17 教训）= 场景级 ±0.08-0.17，而闸门是 −0.05——**闸门宽度小于噪声宽度**。单查询差异不应触发开/关决策。建议场景指标加 bootstrap 置信区间，或闸门只对 all 指标和明确归因的回归生效。
3. **rerank 不可复现**：4 秒超时静默跳过是运行间波动（0.618-0.714）的主嫌。逐条落日志（fired/skipped/耗时），评测轮可 mock 或放大 timeout 冻结行为。
4. **时区/flush ±1 天**：窗口换算统一用「提及于」本地日期而非 created_at UTC；单日窗 ±1 padding 是系统性兜底。
5. **评测 vector 腿双重编码**：`json.dumps({"query": query})` 后再传参，与插件原样传参不一致，需查证服务端解参行为（可能是某次调试遗留）。

**好点子：**

1. **直通降级软信号**（§2.1 D 的产品组件）：overlap=0 时概要段后置/瘦身。自适应、免费、可解释。
2. **deixis linter**（§2.2）：标注时校验 gold ⊆ parse_time_window 窗。扩 60+ 查询前必须就位。
3. **kind=weekly**（§2.2）：周概要直接对齐周级查询，两个文档覆盖两种「上周」口径。
4. **双指标报告**：Recall@上下文 + MRR@10。SC-002 的 12 条增益查询用 Recall@上下文验收更公平。
5. **drill-down 提示行为化**：概要段只保证「日期 + 当日形状」，细节交给 `memobase_search date=`。这其实你们已经做了（FR-017/FR-018），方向正确——#21 的教训只是提醒：概要段行选取要更聪明，而不是把预算盲目加大。
