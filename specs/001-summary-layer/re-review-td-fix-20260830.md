## 2. 复审发现（按严重度）

### F1（P0）「无回归」在 MRR 上是结构性空洞

新度量的实现（L310/L313）：`mixed = event_events`——**两个分支共用同一条事件段管线**。MRR@10 只算事件段（这是双指标的正确设计），但代价是：**hybrid 与对照的 MRR 差异在构造上只可能来自 rerank 运行间噪声**，概要段无法影响它。

逐条 diff 证实：36 条中只有 **#33** 一条 MRR/Recall 不同，且两次运行 top3 第三位不同（hybrid `e5244b52` vs 对照 `2073b998`）——同一管线、同一输入、不同输出 = **rerank 波动铁证**。

### F2（P0）概要段实测贡献 = 0（36/36）

- #33 是唯一差异条。但 #33 的 gold 全部在 **8/25-8/29**，概要拉的是 **8/27 + 8/30** 两天——两天里没有任何 gold 事件。所以连 #33 的 +0.2 recall 也不是概要段给的，仍是 rerank。
- 推论：**概要段对 Recall@union 的 gold 事件贡献，36 条合计为 0**。报告 Δ 表格里 all +0.005 / vague +0.033 全部是单条 rerank 噪声。
- 最尖锐的表述：**当前闸门对概要段质量零敏感**——概要段哪怕注入乱码，MRR/Recall 结果一字不变。这个闸门挡不住坏的概要层，也证明不了好的概要层。

### F3（P0）闸门三方不一致，「通过」不成立

- 评测脚本 L342 **仍执行旧闸门** `all MRR ≥ 0.85` → 两份新 JSON 对应的运行自报「❌ 未通过」（all=0.760）。

## 3. 对报告 §4 五个问题的回答

**Q1：双指标是否合理？**
方向合理（MRR=事件腿排序质量，Recall@union=信息到达），补三点：
1. **rerank 触发/失败状态写进 per_query JSON**（现在只 print，F1 的噪声就是没法从产物审计出来的）；
2. **加「日级命中」作为概要段的本职指标**：gold 日被概要日集覆盖的比例——这是文档段职责的直接度量（本轮 0.50/temporal 0.78）；
3. 行级指标建议直接用**行集**（gold 行文本 ∈ 注入行集），绕开行→事件精确匹配的损耗。

**Q2：概要段价值测不出来，怎么验收？**
分两步：
- **先修截断再测**（F6 第②环）：直通文档行按 BM25(query, 行) 排序或倒序；单日窗预算放宽到 ~700。修完 #21 类查询的行级存活会从 0 直接起来，这时 Recall@union 才有意义。
- **终极验收用 LLM-as-judge 回答质量**：36 条问一遍「带概要段注入 vs 不带，模型回答哪个好」，小样本足够。**「affordance」定位可以接受，但只能作为下限，不能作为目标**——否则 SC-002 那 12 条增益查询的兑现无从谈起。
- 顺序上不要反过来：先用回答质量验收一个截断损坏的概要段，测出来的是截断的锅，不是概要层的锅。

**Q3：查询改写可否接受？**
可以（gold 意图=标注者真实所指，是 ground truth；改查询比改 gold 诚实）。条件：version bump + 改写记录；60+ 扩充前 deixis linter（标注时跑 `parse_time_window` 校验 gold ⊆ 窗）必须就位，否则每轮扩样本都要人工返工。

**Q4：D4 直通降级还要做吗？**
**降优先级，排在截断修复之后**。理由：降级机制保护的是「概要段挤占事件段」的伤害——但当前概要段对指标贡献为 0（F2），无物可保。先把概要段做出可见贡献，再装保险丝。作为生产漂移防护它仍然值得做（~10 行，overlap=0 时概要段后置），放在截断修复 + 重跑之后。

**Q5：开 flag 前必做清单（按序）：**
1. 修 #21 型截断（BM25 行排序 / 倒序 / 单日预算，纯插件侧）
2. 重跑双臂，且：rerank 状态入 JSON + 噪声控制（固定 rerank 结果缓存，或 3 种子取均值）——否则任何 Δ 都无法归因
3. SC-001 正式修订（三方一致：spec 改写、脚本闸门同步、沫沫签核）：建议新闸门 = 事件段 MRR 不低于对照 −0.05 **且 概要段日级命中 ≥ 基线** **且 抽样回答质量不降**
4. SC-002 的 12 条已知增益查询在新度量下重验（旧证据是旧度量产生的）
5. 流程纪律：结果文件永不原地覆盖；queries.yaml version 化
